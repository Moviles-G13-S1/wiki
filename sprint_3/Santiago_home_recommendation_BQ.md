# Santiago's Sprint 3 Business Question

**Question:** What percentage of recommendations displayed on Flutter Home are opened in the recommendation detail view?

This is Type 3 feature usage. It narrows the earlier “Which features are less used?” proposal. Sprint 1 requires at least four Type 3 questions in the final set; the older MS4 list contains three, so the team must still reconcile the full question inventory. Sprint 2 BQ3 measures recommended-product **saves** and continues to use `productEvents`. This question measures the distinct Home card exposures that lead to a detail view. The backend's `recommendation_shown` event is created when a recommendation is generated, so it is not an eligible Home display.

## Counting contract

- Flutter Home's `SmartRecommendationSection` counts a `card_displayed` when at least 50% of its recommendation card is visible on the current route. A card returned from a cache follows the same rule. Widget rebuilds and scroll changes while the card remains mounted do not count again.
- One 128-bit random, lowercase hexadecimal `impressionId` identifies that exposure. A tap on the card records one `detail_opened` with the same ID and navigates to detail. A tap can establish visibility if the detector callback has not yet fired. Repeated taps during the same navigation do not create extra opens. Direct visits to the detail route do not record either event.
- Returning from detail resets the exposure. The card records a new display only when visible on the Home route again. Returning from any other route to the same mounted Home section keeps the existing exposure; remounting Home or loading a new card starts a new exposure if visible.
- Each document in `recommendationHomeEvents` has `userId`, `platform: flutter`, `eventType`, `impressionId`, `recommendationEventId`, and a server `createdAt`. The document IDs are `{impressionId}_display` and `{impressionId}_open`. Firestore rules require authentication, ownership of the referenced backend recommendation event, valid fields and IDs, a server timestamp, and create-only writes. Only admins can read. Kotlin events are excluded.
- The admin callable's `recommendation_home_opens` metric uses a rolling 30 × 24 hour UTC window ending at calculation time. Both a display and its open must be in the window, with matching impression, user, and recommendation IDs, and the open must follow the display. The numerator is distinct paired opens; the denominator is distinct eligible displays; percentage is numerator ÷ denominator × 100, rounded to one decimal. Zero displays returns `percentage: null` (“No data”). Unmatched, duplicate, malformed, and out-of-window events are ignored.

## Delivery and interpretation

The widget writes through `RecommendationController` → `RecommendationRepository` → Firebase Firestore without waiting for the write before navigation. Firestore may queue a write while offline; delivery is not guaranteed if the write ultimately fails. A missing open lowers the numerator. A missing display removes its exposure from the denominator and prevents pairing an open. The percentage is therefore based on **delivered** events, not a guaranteed census of every physical display. A low rate may mean the card already provides enough information or that users save directly from Home; it is not alone evidence of a detail-view problem.

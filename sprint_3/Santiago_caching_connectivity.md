# Santiago: Flutter caching and eventual connectivity

Santiago owns recommendation caching and the Smart Recommendations and Nearby Stores connectivity behavior in Flutter. The [Sprint 3 Business Question](Santiago_home_recommendation_BQ.md) uses the same Home recommendation card but has a separate analytics pipeline. This page describes the implementation in the merged Flutter app, with its limits and demonstration evidence.

## Recommendation data flow and two cache levels

The [For you catalog view](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/views/screens/recommendation_catalog_screen.dart) calls `RecommendationController.getCatalog()`. The [controller](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/controllers/recommendation_controller.dart) checks a per-user [catalog snapshot](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/controllers/recommendation_catalog_snapshot_cache.dart); on a miss the [Firebase repository](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/infrastructure/repositories/firebase_recommendation_repository.dart) calls the backend's [`get_recommendation_catalog`](https://github.com/Moviles-G13-S1/whynot-back/blob/main/functions/recommendations.py). That callable returns distinct unseen products from the user's preferred category and categories represented by saved products. Listing rows does not create a `recommendation_shown` event.

| Data | Structure and key | Freshness and decision |
|---|---|---|
| Full catalog | One immutable list snapshot for the authenticated UID; no LRU ordering is needed for one slot | Nonempty: 5 minutes. Empty: 30 seconds so newly eligible products can appear sooner. A warm revisit skips the catalog callable; Refresh deliberately fetches again. |
| Opened catalog product display details | A separate `RecommendationResultCache<CatalogProductDetails>` with a `LinkedHashMap`, keyed by UID and source product ID; capacity **5** | 5-minute fresh TTL. Reading a hit moves it to the newest position; opening a sixth distinct product evicts the least recently used. A dot on a catalog card indicates its details are currently cached. |
| Home top pick | Another UID-keyed `RecommendationResultCache<ProductRecommendation>`; capacity **8** | Nonempty: 5 minutes. Valid null/no pick: 30 seconds. It is separate from the full catalog and five-product detail LRU. |

The [LRU implementation](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/controllers/recommendation_result_cache.dart) removes and reinserts a hit at the end of its `LinkedHashMap`, then evicts the first key if capacity is exceeded. It tracks hits, misses, evictions, expirations and coalesced requests without storing user or product data in those counters. [Tests](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/test/recommendation_cache_test.dart) exercise cold/warm loads (one versus zero catalog requests), LRU order, TTLs, user isolation, concurrent requests, force refresh and invalidation.

A catalog card opens its product detail immediately from catalog or cached display fields. On **every online** open, including an LRU hit, the backend rechecks eligibility and creates a new saveable recommendation event; offline, the preview remains viewable but Save is blocked. A repeat online open can request `eventOnly: true` and reuse the cached fields. Event IDs and errors are never kept in the five-product display cache; an old event is not reused for Save. See the [backend contract](https://github.com/Moviles-G13-S1/whynot-back/blob/main/docs/recommendation_catalog.md).

The production [dependency graph](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/app/app_dependencies.dart) shares one cache-owning recommendation controller across the views. Auth changes and user switches clear its caches; successful local product, wishlist, demographic-profile and recommendation-save changes invalidate affected recommendation data. Version and user checks reject old in-flight responses after a change. The caches are **in memory only** and do not survive app termination.

## View-specific eventual connectivity

One [ConnectivityStatus](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/controllers/connectivity_status.dart) watches the device transport and app resume. A network transport allows an attempted request but does not prove backend reachability. A successful explicit **Check connection** backend read can correct a stale offline signal. A backend failure while transport is available keeps a retry path rather than claiming the device is offline.

| Flutter view | During connection or service failure | Recovery |
|---|---|---|
| [Home recommendation](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/views/widgets/smart_recommendation_section.dart) | Keeps the last nonempty pick visible with an outdated notice; without one, shows a specific offline or failure state. Saving is unavailable offline. | Retries when connectivity returns or through Check connection; a successful fresh response replaces the fallback. |
| [For you catalog](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/views/screens/recommendation_catalog_screen.dart) | Keeps the last nonempty list visible and marked outdated even after its normal TTL. With no usable list, shows a specific message. The Refresh icon is disabled while confidently offline. | Reconnect or Check connection requests a fresh catalog; a failed refresh does not erase the safe previous list. |
| [Recommendation detail](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/views/screens/recommendation_detail_screen.dart) | Keeps a catalog or cached preview viewable. Save is disabled and explains that it is unavailable offline. | The backend must confirm eligibility and issue a fresh saveable event before Save becomes available; a failed check has a retry. No recommendation save is queued. |
| [Nearby Stores](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/views/widgets/nearby_store_section.dart) | Keeps a previous store and distance only when the [controller](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/lib/controllers/nearby_store_controller.dart) obtains a current location fix within **100 metres** of the original fix for the **same user**. Marks both potentially outdated. Otherwise shows a specific permission, disabled-service, location, or backend failure action. | Rechecks the current location and backend after reconnection or retry; returning from device settings also retries. No store or location write is queued. |

Only a previously successful **nonempty** Home or catalog result is kept beyond the normal freshness TTL as a session-only stale fallback. An empty result is not presented indefinitely as useful offline data. A successful empty refresh clears an older nonempty fallback. Stale display does not establish current product eligibility, and images may fall back while offline.

## Asynchronous execution

- `getRecommendation()`, `getCatalog()`, catalog detail opening and Nearby location/backend reads return **Futures**. Controller and repository calls use `async`/`await` so I/O can complete without freezing the UI; the views use `FutureBuilder` for loading, result and error states.
- Catalog detail opening uses a Future `.then(..., onError: ...)` handler to package either a recommendation or an error while leaving its preview visible. Check connection paths use `.whenComplete(...)` to release their in-progress guard. Home event delivery uses `.catchError(...)` and `unawaited(...)` so telemetry failure cannot block navigation.
- `ConnectivityStatus` subscribes to the connectivity plugin's **stream**; the recommendation controller exposes a broadcast invalidation stream for mounted views. The views also listen to the shared connectivity notifier so an offline-to-online transition can trigger a new request.
- The controller stores in-flight Futures per user to **coalesce concurrent identical requests**. It uses user, version and epoch checks to keep an older completion from repopulating an invalidated cache. These are asynchronous I/O and coordination techniques, not Dart isolates or separate worker threads; no isolate is used for Santiago's features.

## Evidence and limits

- [Flutter cache PR #26](https://github.com/Moviles-G13-S1/whynot-front-flutter/pull/26), [backend catalog PR #27](https://github.com/Moviles-G13-S1/whynot-back/pull/27) and [Flutter connectivity PR #28](https://github.com/Moviles-G13-S1/whynot-front-flutter/pull/28) are merged. The cache redesign reported 110 passing backend tests; the final connectivity branch passed `flutter analyze` and all 106 Flutter tests before its merge. The [connectivity tests](https://github.com/Moviles-G13-S1/whynot-front-flutter/blob/master/test/eventual_connectivity_test.dart) cover stale/no-data, reconnection, stale offline signals, save gating and changed user/location cases.
- The shared [iPhone 16 connectivity evidence](evidence/connectivity_ios/) includes offline recommendation and Nearby screenshots and a refreshed Home after reconnection. The screenshots document those views; they do not by themselves demonstrate every cache eviction, TTL boundary or backend event pairing. Those behaviors have focused automated tests.
- Recommendation product images currently use `Image.network` and a fallback. The app has `cached_network_image` for the **profile photo**, but Santiago's recommendation images do not use that image-cache library. No offline image persistence or restart-safe recommendation catalog is claimed. The backend currently returns the complete eligible catalog in one response; a much larger dataset would need pagination and a response-size policy.
